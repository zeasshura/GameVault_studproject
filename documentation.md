# Архитектура и бизнес-логика проекта GameVault

GameVault — это веб-приложение для ведения личной библиотеки видеоигр, написания детальных рецензий (по критериям Геймплей, Сюжет, Графика, Звук) и организации игр в пользовательские коллекции. Проект разработан с использованием **Django/Django REST Framework** (бэкенд) и **React/Vite/TypeScript** (фронтенд).

В данном документе описывается структура проекта, основные процессы, модели базы данных и API.

---

## 1. Структура проекта

Проект разделен на две основные части:
- **`backend/`**: серверная часть на Python 3 / Django 5.
- **`frontend/`**: клиентская часть на React 18, сборщик Vite.

### Основные директории бэкенда (`backend/`):
- **`apps/`**: директория с Django-приложениями (модулями):
  - `users`: управление пользователями и профилями.
  - `games`: логика работы с каталогом игр, жанрами, платформами, а также интеграция с **RAWG API**.
  - `collections`: управление пользовательскими коллекциями (добавление/удаление игр).
  - `reviews`: логика рецензирования с расширенными оценками.
- **`config/`**: основные настройки Django (`settings.py`, корневой `urls.py`).

### Основные директории фронтенда (`frontend/`):
- **`src/api/`**: модули для взаимодействия с бэкендом (Axios instance, методы для каждого ресурса).
- **`src/components/`**: переиспользуемые UI компоненты (GameCard, ReviewCard, Header).
- **`src/pages/`**: компоненты страниц (Главная, Каталог, Профиль, Детали игры).
- **`src/store/`**: управление глобальным состоянием через **Zustand** (аутентификация, темы).
- **`src/types/`**: TypeScript интерфейсы данных.

## 2. Модели базы данных и Миграции

БД (PostgreSQL / SQLite) содержит следующие основные сущности:

### `users.User`
Кастомная модель пользователя, наследованная от `AbstractUser`. Содержит:
- `avatar_url` — ссылка на аватар профиля.
- `bio` — описание профиля.

### `games.Game`
Хранит информацию об игре.
- Поля: `title`, `description`, `cover_url`, `video_url`, `release_date`.
- Рейтинги: `avg_rating` (средний рейтинг на платформе), `initial_rating` и `initial_rating_count` (данные, подтянутые из RAWG для взвешенного среднего).
- Связи: Многие-ко-многим с `Genre` и `Platform` (через промежуточные таблицы `GameGenre` и `GamePlatform`).

### `reviews.Review`
Отзывы пользователей.
- Поля: `text`, `score` (общий балл).
- Расширенная система оценок (добавлена последней миграцией):
  - `score_gameplay`, `score_story`, `score_graphics`, `score_sound`.
  - Общий `score` вычисляется на фронтенде как среднее значение этих четырёх параметров.
- Связи: `user` (ForeignKey на User) и `game` (ForeignKey на Game).

### `collections.Collection`
Пользовательские коллекции игр.
- Поля: `name` (название коллекции).
- Связи: `user` (ForeignKey), `games` (ManyToManyField к `Game`).

**Миграции:**
Все изменения структуры БД сохраняются в директориях `migrations/` каждого приложения. 
Команда для применения: `python manage.py migrate`. При развертывании в Docker это происходит автоматически при инициализации или вручную через `docker compose exec backend python manage.py migrate`.

## 3. Бизнес-логика и Процессы

### 3.1 Интеграция с RAWG API (Наполнение каталога)
Проект не заставляет пользователей вводить игры вручную, а использует открытую базу **RAWG API**.

**Процесс:**
1. **Поиск (Search):** При вводе названия в строку поиска на фронтенде отправляется запрос на `GET /api/games/search/?q=...`. Бэкенд делает прокси-запрос к `api.rawg.io/api/games?search=...`, фильтрует результаты и возвращает на фронт.
2. **Импорт (Import):** Когда пользователь нажимает на неимпортированную игру из результатов поиска, фронтенд шлет запрос `POST /api/games/import/` с `rawg_id`.
3. Бэкенд (`apps.games.views.import_rawg`):
   - Делает детальный запрос к RAWG API (с `lang=ru` для русского языка).
   - Очищает `description` от HTML-тегов с помощью встроенной утилиты Django `strip_tags`.
   - Дополнительно делает запрос к `/movies`, чтобы получить URL трейлера (`video_url`).
   - Сохраняет игру, жанры, платформы в локальную БД через транзакцию `update_or_create`.
   - Подтягивает базовые оценки от RAWG (`ratings_count` и `rating`), которые используются для расчета средневзвешенного рейтинга, чтобы одна оценка пользователя "1/10" не обрушила рейтинг популярной игры.

### 3.2 Расчет взвешенного рейтинга
При написании рецензии (`apps.reviews.views`) триггерится пересчет среднего рейтинга игры.
Формула в `Game.update_rating()`:
`Новый Рейтинг = (Сумма локальных оценок + (initial_rating * initial_rating_count)) / (Кол-во локальных рецензий + initial_rating_count)`
Это защищает игры от резких скачков рейтинга (Review Bombing), если у игры уже была огромная база оценок на RAWG.

### 3.3 Аутентификация
В проекте используется **JWT (JSON Web Tokens)** через библиотеку `djangorestframework-simplejwt`.
- `POST /api/users/auth/login/` — выдает `access` и `refresh` токены.
- Фронтенд (через Zustand + Axios Interceptors) автоматически подставляет `access` токен в заголовок `Authorization: Bearer <token>` ко всем приватным ручкам.
- Если `access` токен истек, Axios Interceptor ловит `401 Unauthorized`, шлет `refresh` токен на `/api/users/auth/refresh/`, обновляет стейт и прозрачно повторяет изначальный запрос.

### 3.4 Взаимодействие (Коллекции и Рецензии)
- **Коллекции:** Пользователь может создать коллекцию "Пройдено" и добавить туда игру. Фронтенд шлет `POST /api/collections/` и `POST /api/collections/{id}/add_game/`. 
- **Рецензирование:** Пользователь выставляет 4 критерия (Геймплей, Сюжет, Графика, Звук). Фронтенд усредняет их и отправляет в `POST /api/reviews/games/{game_id}/reviews/`. Сериализатор валидирует, что пользователь оставляет только один отзыв на конкретную игру (через `exists()` проверку в `ReviewWriteSerializer`).

## 4. Основные API Эндпоинты (Ручки)

### Users API (`/api/users/`)
- `POST /auth/register/` - Регистрация.
- `POST /auth/login/` - Получение JWT.
- `GET/PUT /profile/` - Просмотр/редактирование своего профиля.
- `GET /{id}/` - Публичный профиль другого пользователя.

### Games API (`/api/games/`)
- `GET /` - Пагинированный список игр (с поддержкой фильтрации по жанрам и поиску).
- `GET /{id}/` - Детальная информация об игре.
- `GET /search/?q=` - Поиск игр во внешней базе RAWG.
- `POST /import/` - Импорт конкретной игры из RAWG в локальную БД.

### Reviews API (`/api/reviews/`)
- `GET /games/{id}/reviews/` - Получить все отзывы к игре.
- `POST /games/{id}/reviews/` - Написать отзыв.
- `PUT/DELETE /{id}/` - Изменить или удалить свой отзыв.

### Collections API (`/api/collections/`)
- `GET /` - Получить все свои коллекции со вложенными играми.
- `POST /` - Создать коллекцию.
- `POST /{id}/add_game/` - Добавить игру в коллекцию.
- `DELETE /{id}/remove_game/` - Удалить игру.

## 5. Технологические особенности защиты проекта
Если вам зададут вопросы по архитектуре, обратите внимание на следующие решения:
1. **Zustand вместо Redux:** используется для более легкого и быстрого управления глобальным состоянием фронтенда (сохранение JWT в localStorage, управление темой).
2. **Axios Interceptors:** автоматическое продление сессии (refresh token) без выброса пользователя на окно логина.
3. **TailwindCSS / Vanilla CSS:** Для реализации дизайна "в стиле RAWG / Steam" использованы кастомные CSS переменные в связке с utility-классами.
4. **DRF Serializers:** Строгое разделение на `ReviewSerializer` (для чтения с детальной информацией о пользователе) и `ReviewWriteSerializer` (только нужные поля для безопасной записи).
5. **Безопасность транзакций:** В `views.py` во время создания игры (`update_or_create`) используется `with transaction.atomic()`, чтобы при сбое (например, ошибка БД при привязке жанра) не создавались "полупустые" или битые записи в каталоге.
